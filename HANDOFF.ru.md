# Состояние работы и передача контекста

Этот файл — для того, кто продолжает работу над проектом (человека или новой сессии Claude Code).
README описывает, **что** получилось; здесь — **как оно устроено внутри, что уже проверено, на какие
грабли я наступил и что осталось**.

Ничего машинно-специфичного здесь нет: адреса, имена хостов и доступы в публичный репозиторий не
кладём.

---

## 1. Из чего состоит

| Файл | Что делает | Язык |
|---|---|---|
| `yasync.py` | Движок. Конфиг, выбор хранилища и папок, запуск `rclone bisync`, поиск конфликтов, снимки общего предка, HTTP-сервер страницы слияния | Python, только стандартная библиотека |
| `yadiff.py` | Разбор файлов в строки (включая офисные), трёхстороннее сравнение, генерация страницы слияния | Python, только стандартная библиотека |
| `CloudSync.swift` | Приложение в строке меню. Выбор хранилища и папок, состояние, и решение **когда** синхронизировать | Swift, один файл, `swiftc`, без Xcode |

Внешняя зависимость ровно одна — `rclone`. Токены хранит он, мы их не читаем и не логируем.

---

## 2. Установка и обновление на Mac

```bash
cp yasync.py yadiff.py ~/bin/ && chmod +x ~/bin/yasync.py
swiftc -O CloudSync.swift -o ~/bin/CloudSync
```

Приложение в строке меню из SSH-сессии **не поднимется**: `launchctl asuser` требует root, а процесс,
запущенный из ssh, не достаёт до оконного сервера. Рабочий способ — агент launchd:

```bash
launchctl bootout   gui/$(id -u)/com.local.cloudsync 2>/dev/null
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.local.cloudsync.plist
launchctl print     gui/$(id -u)/com.local.cloudsync | grep -E "state|pid"
```

Plist приложение умеет писать само — пункт меню «Запускать при входе».

## 3. Как проверять

**Движок** — без графики:

```bash
python3 ~/bin/yasync.py remotes          # что знает rclone
python3 ~/bin/yasync.py status
python3 ~/bin/yasync.py state            # то же в JSON, это читает приложение
python3 ~/bin/yasync.py conflicts
```

**Страницу слияния** — с фиксированным портом, чтобы адрес не менялся от запуска к запуску:

```bash
python3 ~/bin/yasync.py resolve <файл> --port 8920 --no-browser &
curl -s http://127.0.0.1:8920/ -o /tmp/p.html
```

Логика страницы целиком в JS, поэтому статический снимок HTML почти ничего не доказывает.
**Проверять надо в живой странице**, вызывая её же функции: `startEdit`, `commitEdit`, `addSide`,
`removeSide`, `movePick`, `autoMerge`, `undo`, `redo`, а состояние читать из `D.blocks` и
`mergedLines()`. Так проверены все случаи из раздела 5.

Данные для страницы лежат в `const D = {...}` — можно вытащить регуляркой и разобрать как JSON.

## 4. Решения, которые нельзя откатывать не подумав

**Никакого фонового опроса.** Ни таймеров, ни циклов. Четыре источника пробуждения, все push:
FSEvents на корне, активация Finder (не чаще раза в 2 минуты), `didWakeNotification`, возврат сети
через `NWPathMonitor`. Это прямое требование владельца: «наша штука не должна вечно крутиться в фоне
и жрать батарею». Любой `Timer.scheduledTimer` здесь — регресс.

**События «папку открыли» в macOS не существует.** Публичного API нет, Finder ничего не рассылает.
Активация Finder — приближение, и его нельзя выдавать за настоящий сигнал.

**Страховку `bisync` не обходим молча.** `Safety abort` / `all files were changed` ловит случайно
перемещённую или очищенную папку. Движок останавливается, пишет `lastResult: needs-confirm` с
причиной, и `--force` добавляется только после явного подтверждения человеком в диалоге, который
показывает, что именно сказал `bisync`. Автоматический `--force` сделал бы инструмент удобным и
изредка катастрофическим.

**Конфликт обязан оставлять обе версии.** Это даёт связка
`--conflict-resolve none --conflict-loser pathname --conflict-suffix local,remote`. Уберёшь — исчезнет
вход для диффа, и слияние станет не из чего делать.

**Провайдер не зашит.** Хранилище берётся из настроенных remote `rclone`. Про конкретный бэкенд знает
ровно одна строка — `BACKEND_FLAGS["yandex"] = --yandex-upload-wait 2s` (у Яндекса загруженный файл не
сразу виден в листинге, и `bisync` без паузы считает его пропавшим). Другому провайдеру — своя строка
там же.

**Каталог состояния — `CloudSync`, но старый `YandexSync` подхватывается, если он есть.** Переносить
живое состояние `bisync` на ходу опаснее, чем искать в двух местах. По той же причине корень
синхронизации не переезжает из-под папок, которые уже синхронизируются.

## 5. Трёхстороннее слияние — суть

**Двух версий для автослияния мало.** Строка есть слева и нет справа — это либо «слева добавили»,
либо «справа удалили». Дифф эти случаи не различает. Время файла тоже не помогает: у файла один
`mtime` на весь файл, построчной истории на диске нет нигде.

Поэтому движок хранит третью версию сам: после каждой удачной синхронизации, когда стороны сведены по
определению, снимок папки уходит в `~/Library/Application Support/CloudSync/base/` — gzip,
инкрементально по размеру и `mtime`, файлы больше 32 МБ пропускаются. Файлы, которые **сейчас в
конфликте, намеренно не переснимаются**: их старый предок и нужен слиянию.

`build_blocks3(base, a, b)` раскладывает каждый участок:

| Обе стороны относительно предка | `auto` |
|---|---|
| изменилась только левая | `["left"]` |
| изменилась только правая | `["right"]` — **включая удаления** |
| обе изменились одинаково | это не различие, участок помечается как совпадающий |
| обе изменились по-разному | `None`, решает человек |

Без предка (`build_blocks` с `base=None`) однозначна только односторонняя вставка, и страница честно
пишет «общего предка нет», а счёт помечает приблизительным.

**Состояние участка — пара `{picks, manual}`:**
- `picks` — массив сторон **в порядке нажатия**; порядок нажатий задаёт порядок строк, поэтому кнопки
  «взять оба» не нужны;
- `manual` — строки, введённые руками; перекрывают `picks`, но не стирают их.

История отмены хранит обе части целиком (`snap` / `applyState`), поэтому ручная правка отменяется так
же, как нажатие стрелки, а стрелка поверх ручной правки заменяет её обратимо.

**Итоговый текст всегда собирается из `mergedLines()`** — того, что видно в центре. Сервер
(`apply_resolution`) предпочитает присланный `text`, если он есть.

## 6. Грабли, на которые я уже наступил

1. **Порядок колонок в CSS-сетке.** Ячейки добавляются «номер строки, потом текст». Шаблон должен
   заканчиваться на `46px 1fr`, а не `1fr 46px`, иначе правая панель схлопывается в один символ, а
   результат визуально уезжает к краю. Проверять измерением: три текстовые дорожки должны быть
   примерно равны.
2. **Проекция границы участка в трёхстороннем алгоритме неоднозначна** на стыке «конец совпадения +
   вставка нулевой ширины». Нужны две проекции: для начала участка самая ранняя, для конца самая
   поздняя (`_project(..., end=True)`). Иначе вставка в конец файла молча теряется.
3. **Фон в CSS перекрывает SVG.** Полосы-связки рисуются в `<svg>` под ячейками; у `.gut` должен быть
   `background:none`, а разделитель рисуется прямоугольником внутри самого SVG.
4. **Заголовки колонок должны быть внутри прокручиваемой области** (`position:sticky`), иначе ширина
   полосы прокрутки их рассинхронизирует.
5. **`screencapture` по ssh отдаёт только обои** — у sshd нет разрешения на запись экрана. Проверять
   состояние графики так бессмысленно. А вот `webbrowser.open` из ssh **работает**, страница
   открывается на экране Mac; проверять через `osascript -e 'tell application "Safari" to get URL of
   front document'`.
6. **Длинные heredoc через инструмент запуска команд рвутся**, а экранирование в них может
   схлопнуться: `\\n` однажды превратился в настоящий перенос строки прямо внутри JS-строки и уронил
   всю страницу. Правки в файлы лучше делать файловыми инструментами, а не через shell.
7. **Собственная запись поднимает FSEvents.** Без окна тишины (сейчас 5 с после синхронизации)
   приложение заводит само себя по кругу. Обратная сторона: правка, сделанная ровно во время
   синхронизации, уедет не мгновенно, а при следующем событии.

## 7. Что уже проверено на живой машине

- `swiftc -O CloudSync.swift` — собирается без единой ошибки и предупреждения; приложение живёт под
  launchd в графической сессии.
- Настоящий конфликт с настоящим предком: все пять участков разложены верно — три однозначных, два
  спорных; удаление опознано как удаление.
- Снимок предка пишется и читается (`gzcat` отдаёт исходный текст), манифест инкрементальный.
- Стрелки: взять, вернуть (стрелка разворачивается), добавить вверх/вниз, ↑↓ меняют порядок, значки
  порядка 1/2 совпадают с порядком строк в результате.
- Автослияние: гаснет, когда применять нечего, оживает после отмены, **не трогает спорные участки**.
- Правка на месте: правится и различие, и совпадающий участок; отмена и возврат работают; стрелка
  поверх правки заменяет её обратимо.
- Переход на новое имя (`CloudSync`) не сломал существующую установку: папки, конфиг и конфликты на
  месте, метка хранилища подтянулась автоматически.

## 8. Что не сделано

**Слияние офисных файлов.** Сейчас `.docx/.doc/.rtf/.odt` (через `textutil`) и `.xlsx/.pptx` (zip+XML
стандартной библиотекой) **только показываются**: видно, что изменилось, но собрать документ обратно
из текста нельзя, поэтому предлагается выбрать версию целиком.

Как сделать по-настоящему, если браться: `.docx` — это zip, внутри `word/document.xml`, абзацы —
элементы `<w:p>`. Сравнивать абзацы по их тексту, а результат собирать из **исходных XML-элементов**
каждой стороны — тогда форматирование переживает слияние, потому что элемент переносится целиком.
Честное ограничение, которое надо будет обработать: абзац с картинкой, сноской или гиперссылкой
ссылается на `word/_rels/document.xml.rels`, и перенос такого абзаца с чужой стороны требует переноса
ссылки, иначе документ будет битым. Начинать стоит с `.docx`; `.xlsx` сложнее (общие строки, формулы),
`.xls`/`.ppt` (старые двоичные) не читаются вообще.

**Остальное:**
- Конфликт, возникший раньше первого снимка, разбирается двусторонним запасным путём — это by design,
  но стоит подсказывать пользователю, что предок появится после первой синхронизации.
- У файлов больше 32 МБ предка нет и не будет.
- Метки Finder и ресурсные вилки круговой рейс не переживают — это забота `rclone`, не наша.
- Приложение не проверяли на втором провайдере (всё гонялось на Яндекс.Диске). Код провайдер-
  независимый, но это **не проверено** — первый же запуск на Google Drive или S3 стоит считать
  проверкой, а не данностью.
- Нет ни одного автоматического теста. Трёхсторонний алгоритм — чистые функции без ввода-вывода
  (`build_blocks3`, `_project`, `pair_lines`, `block_result`), их легко накрыть `unittest`; это
  первое, что стоит сделать, если браться за docx.
